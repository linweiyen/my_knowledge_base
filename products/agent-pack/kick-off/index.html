1. 產品背景與替代關係

  • 我們主要銷售 GPU、工作站與伺服器；許多小型客戶只買一台工作站（例如兩張 GPU），首先希望跑起大語言模型，不想自行安裝 Ollama 等工具。
  • AIDMS 基於 Kubernetes 管理多台 node，對這類客戶的安裝與維護成本過高。
產品 後續方向 對本專案的意義
RTX Pack 準備 Phase out，由 Agent Pack 取代 參考經驗，重新設計使用體驗
GDMS 準備 Phase out 不預設承接全部能力或架構
Agent Pack 新的單機 AI 管理產品 開箱即用：管理資源、模型與 Agent Container
AIDMS 持續管理多台 GPU node 保留多節點產品分工；客戶擴充時的升級路徑

產品目的：以較低的部署與維護成本，讓單台設備開箱就能跑起 AI 工作負載。

3. 產品定位與原則

隨 GPU 工作站出貨、基於 Docker 的單機 AI 管理軟體：通用容器平台加驗證過的 image 目錄，管理 GPU、部署大語言模型、運行 Agent Container。

已確認方向 仍需確認的設計
一台工作站或單機伺服器 首發硬體、GPU、OS 與版本
Docker，不採 Kubernetes 部署拓樸與安裝包裝方式
不建立產品帳號 本機入口、管理權限與遠端存取
三種 GPU 配置需求 共享方式、限制與隔離能力
預整合 Agent＝驗證過的普通 image 首版 image 目錄清單、相容 image 約定

價值在「裝好、驗過、有人維護」，不重做開源引擎；Ollama、vLLM、Open WebUI 是包進去的原料。

4. 核心情境

情境 操作 驗收
A. 雙 GPU 跑一個大模型 資源總覽確認兩卡可用 → 建立模型服務選 GPU 0、1 → 套用驗證過的跨卡設定 → 送出測試請求 容器取得兩卡，模型確實利用多卡完成推論
B. 同機運行多個工作 整卡分開、同卡共享、新工作超過資源時提示衝突 指派與實際使用一致；共享限制明示；可停止與恢復
C. 接入 image 上傳 tar 或由 registry 取得 → 填入 GPU、環境變數、連接埠、掛載 → 模型 API 位址自動注入 → 啟動看日誌 依接入規則部署、成功呼叫模型，停止與重啟後符合設定

情境 C 同時涵蓋客戶自製 image 與目錄中驗證過的 image，兩者走同一條路。
