## Agent Pack (RTX Pack 2.0)
### 產品規劃啟動會議

單機 GPU 資源、模型服務與 Agent Container 管理

:::notes
本版由 26 頁精簡為 10 頁，並依 2026-10-22 決策更新：預整合 Agent 以驗證過的 Docker image 提供，第一版不依賴 NemoClaw／OpenShell。原 26 頁版本保留於 Git 歷史（2026-10-21 提交）。RTX Pack 與 GDMS 準備退場；面向單台設備的小型客戶；採 Docker、不採 Kubernetes；免帳號管理。具體硬體、共享方式、初版範圍、工期與維護責任仍待規劃。

## 1. 產品背景與產品線分工

- 起因為許多小型客戶只買一台工作站（例如四張 GPU 以內），首先希望跑起大語言模型，不想自行安裝 Ollama 或 vLLM 等工具。
- AIDMS 2.0 基於 Kubernetes 管理多台 node，對這類客戶的安裝與維護成本過高。

| 產品 | 後續方向 | 對本專案的意義 |
|---|---|---|
| RTX Pack | 升級為 Agent Pack | 延續既有經驗，重新設計使用體驗 |
| GDMS | 後續整併方向另行規劃 | 不預設承接全部能力或架構 |
| Agent Pack | 新的單機 AI 管理產品 | 開箱即用：管理資源、模型與 Agent Container |
| AIDMS | 持續管理多台 GPU node | 保留多節點產品分工；客戶擴充時的升級路徑 |

**產品目的：以較低的部署與維護成本，讓單台設備開箱就能跑起 AI 工作負載。**

:::notes
背景來自使用者說明，未引用市場規模。四張 GPU 以內是代表情境，不是限定出貨規格。成本改善是目標，尚無量測結果，需比較安裝工時、環境依賴及維護支援投入。產品線分工由使用者明確指定；不推定所有 GDMS 客戶都遷移至 Agent Pack，退場時程與既有客戶服務另行規劃。
:::

## 2. 產品定位與原則

> 隨 GPU 工作站出貨、基於 Docker 的單機 AI 管理軟體：通用容器平台加驗證過的 image 目錄，管理 GPU、部署大語言模型、運行 Agent Container。

| 已確認方向 | 仍需確認的設計 |
|---|---|
| 一台工作站或單機伺服器 | 初版硬體、GPU、OS 與版本 |
| Docker，不採 Kubernetes | 部署拓樸與安裝包裝方式 |
| 免帳號管理 | 本機入口、管理權限與遠端存取 |
| 三種 GPU 配置需求 | 共享方式、限制與隔離能力 |
| 預整合 Agent＝驗證過的普通 image | 初版 image 目錄清單、相容 image 約定 |

不重做開源引擎，只做「裝好、驗過、有人維護」；Ollama、vLLM、Open WebUI（待評估）是原料。

:::notes
早期曾討論個人 AI 助理工作站、企業部門 Agent 套件、Agent 部署工具三個方向，現收斂為單機資源與容器管理基礎，其他作為後續應用情境（見 positioning 討論稿）。免帳號管理不代表免除 OS 權限、模型 API key 或遠端存取保護。2026-10-22 決策：第一版不依賴 NemoClaw／OpenShell，研究中的 DinD 不成為既定架構，詳見決策紀錄。對免費工具的差異化：硬體驗證組合、單一支援窗口、GPU 分配與衝突管理、還原到出廠狀態、內網離線可裝、升級到 AIDMS 的路徑。
:::

## 3. 工作負載與三種 GPU 配置

| 工作負載 | 客戶如何使用 | Agent Pack 管理什麼 |
|---|---|---|
| 大語言模型服務 | Container 執行模型並提供 OpenAI 相容 API | 啟停、GPU、連線、狀態及日誌（待評估） |
| 客戶自製 Agent | 自製 image 上傳或由 registry 取得 | image、參數、掛載、模型位址注入 |
| 驗證 image 目錄 | 模型服務、對話介面（Open WebUI，待評估）、Agent | 與自製 image 同一機制，另加目錄頁 |

| GPU 配置 | 配置例子 | 需要呈現的結果 |
|---|---|---|
| 整張 GPU 分配 | Container A 用 GPU 0，B 用 GPU 1 | 各容器指派的 GPU 與占用 |
| 單張 GPU 共享 | A、B 共用 GPU 0 | 共享關係、用量及支援限制 |
| 單一容器跨多卡 | A 使用 GPU 0、GPU 1 | 模型實際跨卡運行 |

:::notes
Agent 可連接同機模型服務或指定的外部模型 API；並非每個 Agent 都需直接取得 GPU。單卡共享分兩層：API 層（一個模型服務占 GPU，多個 Agent 共用其 API）優先，GPU 層依硬體驗證；工作站等級 RTX 卡無 MIG，誠實答案可能是時間切片共享加 VRAM 可視與超額警告，不是硬體隔離。多卡需分開驗證容器可見性與模型服務實際 tensor parallel，取決於推論引擎、模型大小與 PCIe／NVLink 拓樸。初版 image 目錄可以很小：一個模型服務加一個對話介面即達成開機可用；OpenClaw、Hermes 是否納入依技術驗證結果決定。
:::

## 4. 核心情境

| 情境 | 操作 | 驗收 |
|---|---|---|
| A. 雙 GPU 跑一個大模型 | 資源總覽確認兩卡可用 → 建立模型服務選 GPU 0、1 → 套用驗證過的跨卡設定 → 送出測試請求 | 容器取得兩卡，模型確實利用多卡完成推論 |
| B. 同機運行多個工作 | 整卡分開、同卡共享、新工作超過資源時提示衝突 | 指派與實際使用一致；共享限制明示；可停止與恢復 |
| C. 接入 image | 上傳 tar 或由 registry 取得 → 填入 GPU、環境變數、連接埠、掛載 → 模型 API 位址自動注入 → 啟動看日誌 | 依接入規則部署、成功呼叫模型，停止與重啟後符合設定 |

**情境 C 同時涵蓋客戶自製 image 與目錄中驗證過的 image，兩者走同一條路。**

:::notes
情境 A：尚未指定模型與效能門檻，不承諾所有模型可跨卡或效能倍數。情境 B：共享不等於固定比例切割，不在此指定 MIG／MPS。情境 C 需定義：image 來源（tar 載入、公開或內部 registry、離線）、相容 image 約定（base URL 環境變數、健康檢查路徑、持久化目錄）、安全邊界（預設不給 privileged、不掛 Docker socket、GPU 只給指定卡）、支援責任（平台與目錄 image 由我方支援，客戶自製 image 內容不在範圍）。容器停止不一定取消已送到外部服務的請求。
:::

## 5. 現有基礎、缺口與工程風險

| 面向 | 目前可沿用的基礎 | 還要補的能力 |
|---|---|---|
| 安裝與維護 | RTX Pack／GDMS／License Server 相關程式碼、技術文件與經驗 | 簡化交付、狀態、診斷、更新、還原到出廠狀態 |
| 模型服務 | 連接既有模型 API | 本機模型 Container 部署與管理 |
| 資源配置 | AIDMS 1.0（Docker）與 AIDMS 2.0（Kubernetes）的 GPU 資源配置 | 評估是否加入 MIG |
| image 接入 | OpenClaw／Hermes 設定、記憶、任務取消研究 | 通用接入規則、相容約定、Docker 層圍欄 |

**優先風險**：GPU 共享與多卡模型實測；設定與資料在重啟、重建、更新後完整可用；運行與停止狀態真實可信；內網離線安裝。

:::notes
依據：全庫閱讀報告 §3–5、§7 與來源索引。研究庫是安裝、維運與實測研究庫，不是完成的管理產品；沒有獨立的 Agent Pack 管理前後端。研究中共享推論路由、rebuild 資料遺失、每次啟動下載腳本等限制多來自 NemoClaw／OpenShell 包裝層，新拓樸下不直接適用，但需重新驗證。歷史 A100 MIG 教學不能當成新版各型 GPU 的支援證據。舊產品將退場，參考經驗不代表沿用原架構。
:::

## 6. 第一版能力範圍與待定事項

| 能力範圍 | 候選交付 | 定案前需決策 |
|---|---|---|
| 單機管理入口 | 免帳號管理、資源總覽與基本診斷 | 管理入口、OS 權限及遠端存取範圍 |
| 容器管理 | image 取得／上傳、建立、啟停、日誌及移除 | image 來源與相容約定、安全邊界 |
| GPU 配置 | 整卡分配、同卡共享、單一容器跨多卡 | 初版硬體、GPU 型號與數量、OS、共享方案 |
| 模型服務 | 本機模型部署流程與 API 連線資訊 | 首個推論引擎與模型清單 |
| 驗證 image 目錄 | 模型服務＋對話介面（Open WebUI，待評估）＋候選 Agent | 初版目錄清單；Agent 依技術驗證決定 |
| 維護 | 設定保存、開機恢復、備份還原、使用者自助災難復原與文件 | 預裝或安裝包、更新、既有客戶升級方案與責任 |

多節點排程、企業帳號系統、Agent policy 管制層，列為後續範圍。

:::notes
需求已對齊，出貨範圍仍需估工。不因第一版而靜默刪掉同卡共享或多卡需求；若需分期必須提出影響並取得決策。建議第一版以一條垂直切片驗證：全新四卡以內的機器 → 安裝 → 模型跨多卡跑起來 → 提供 API → 一個 Agent image 接上。預裝與安裝包可並存，但測試及維護投入需估算。模型、映像與第三方元件散布授權需於交付前核對。定價是否隨機附贈、維護期限另行確認。
:::

## 7. 驗收與執行階段

| 驗收項目 | 必須提供的證據 |
|---|---|
| 整卡分配／單卡共享 | 指派與使用一致；同卡兩個工作量測資源競爭、失敗與恢復 |
| 單容器跨多卡 | 可見多張 GPU，實際模型完成跨卡推論 |
| image 接入 | image 匯入、配置、呼叫模型、查看日誌、重啟後符合設定 |
| 日常維護 | 停止、開機恢復、備份還原，資料符合保存清單 |
| 災難復原（使用者自助） | 系統 crash 後，客戶依文件自行還原到出廠狀態或從備份復原，不需原廠介入；記錄步驟數與時間 |
| 交付成本 | 工廠／夥伴預裝工時；客戶開機到模型可用的時間與人工介入；交機後支援工時。基準為現行出貨方式 |

**執行階段**：A 產品規劃 → B 可行性驗證 → C 第一版整合 → D 試用與交付。

:::notes
執行階段產出：A 初版規格、範圍、估工；B 三種 GPU 配置與模型／image PoC；C 管理入口、Docker 部署、文件；D 試用回饋、問題關閉、支援方案。結果需對應 GPU 型號、模型、image 及版本，明列共享的保證範圍。災難復原是降低維運成本的關鍵：需定義「出廠狀態」涵蓋什麼（管理服務、模型、image 目錄、設定）、備份清單包含什麼、復原後哪些資料會遺失，並由非工程人員照文件實際演練一次。量化門檻於 PoC 建立基準後核定；建議在評審前先用一台現有四卡以內的機器量測現行流程的安裝工時，否則「降低成本」沒有基準。各階段日期與預算未核定，評審需同時提交範圍、估工、硬體測試依賴及成本。
:::
