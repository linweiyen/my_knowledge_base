## Agent Pack
### 產品規劃啟動會議

單機 GPU 資源、模型服務與 Agent Container 管理

取代 RTX Pack 的新產品　2026-10-21

:::notes
本次依最新共識重寫。RTX Pack 與 GDMS 準備退場，重新設計 Agent Pack 取代 RTX Pack；面向單台設備的小型客戶；採 Docker、不採 Kubernetes；不建立產品帳號；支援三種 GPU 配置需求。具體硬體、共享方式、首版範圍、工期與維護責任仍待規劃。本次是產品規劃 kick off。

## 1. 產品背景與成本壓力

### 一台雙 GPU 工作站，也需要合適的管理軟體

- 我們主要銷售 GPU、工作站與伺服器。
- AIDMS 基於 Kubernetes 管理多台 node，帶來安裝部署與維護成本壓力。
- 許多小型客戶只購買一台工作站，例如兩張 GPU，首先希望跑起大語言模型。
- 這類客戶改由 Agent Pack 提供單機管理能力。

**產品目的：以較低的部署與維護成本，讓單台設備的 AI 工作負載容易使用與管理。**

:::notes
本頁背景來自使用者說明，未引用市場規模。雙卡是代表情境，不是限定出貨規格。成本改善是目標，尚無量測結果。後續需比較安裝工時、環境依賴及維護支援投入。
:::

## 1. 產品替代關係

| 產品 | 後續方向 | 對本專案的意義 |
|---|---|---|
| RTX Pack | 準備 Phase out，由 Agent Pack 取代 | 參考經驗，重新設計使用體驗 |
| GDMS | 準備 Phase out | 不預設承接全部能力或架構 |
| Agent Pack | 新的單機 AI 管理產品 | 管理資源、模型與 Agent Container |
| AIDMS | 持續管理多台 GPU node | 保留多節點產品分工 |

Agent Pack 重新設計以取代 RTX Pack，GDMS 的能力承接另行決定。

:::notes
替代關係由使用者明確指定。不推定所有 GDMS 客戶都遷移至 Agent Pack。產品退場時程、既有客戶服務及資料遷移方式仍需規劃。
:::

## 1. 商業價值與衡量方式

| 預期價值 | 產品做法 | 後續量測 |
|---|---|---|
| 降低單機交付成本 | Docker 部署、固定支援組合 | 安裝工時、人工介入、支援工時 |
| 提高硬體可用性 | 啟動模型，查看 GPU 與容器狀態 | 首次成功時間、運行成功率 |
| 支持硬體展示與採用 | 展示雙卡模型及同卡共享 | 展示、試用及方案採用紀錄 |
| 降低後續維護負擔 | 診斷、設定保存與恢復 | 問題處理時間與更新結果 |

以上為預期改善方向，成效與目標值需建立基準後確認。

:::notes
建議用相同硬體及任務，比較現行流程和 Agent Pack PoC。不因不採 Kubernetes 就宣稱已降低多少成本。定價、是否隨機附贈、維護期限及客製服務範圍另行確認。
:::

## 3. Agent Pack 的產品定位

> 隨 GPU 工作站與伺服器提供、基於 Docker 的單機 AI 管理軟體，協助小型客戶管理 GPU 資源、部署大語言模型，以及運行自製或預先整合的 Agent Container。

**使用方式：免建立產品帳號，直接管理這一台設備。**

客戶負責自己的應用邏輯與資料，我們提供經驗證的部署、資源配置及日常管理能力。

:::notes
免產品帳號不代表免除 OS 權限、模型 API key 或遠端存取保護。管理入口的本機／遠端範圍仍需明確定義。不能將免帳號推導為任何網路使用者皆能操作主機。
:::

## 3. 已確認原則與待定設計

| 已確認方向 | 仍需確認的設計 |
|---|---|
| 一台工作站或單機伺服器 | 首發硬體、GPU、OS 與版本 |
| Docker，不採 Kubernetes | 部署拓樸與安裝包裝方式 |
| 不建立產品帳號 | 本機入口、管理權限與遠端存取 |
| 三種 GPU 配置需求 | 共享方式、限制與隔離能力 |
| 模型與 Agent Container | 自製容器規則與預整合名單 |

研究中的 DinD 不自動成為新產品的既定架構。

:::notes
Docker 是使用者基於維護考量確認的原則。三種 GPU 需求已確認，不等於任意硬體可任意百分比切割。首發 OS、Docker 編排與包裝尚未核定。
:::

## 3. 三類工作負載

| 類型 | 客戶如何使用 | Agent Pack 管理什麼 |
|---|---|---|
| 大語言模型服務 | Container 執行模型並提供推論 | 啟停、GPU、連線、狀態及日誌 |
| 客戶自製 Agent | 將自製 Agent 包成 Container 匯入 | 映像、參數、掛載與運行 |
| 預先整合的 Agent | 選用 OpenClaw、Hermes 等候選環境 | 經驗證的安裝、設定與使用入口 |

Agent 可連接同機模型服務，或指定的外部模型 API。

:::notes
OpenClaw 與 Hermes 已有 GitLab 可行性研究，但不代表兩者皆完整納入第一版。自製容器以共通資源及生命週期管理為主，不預設可管理其內部對話、記憶與任務語意。並非每個 Agent 都需直接取得 GPU，可由模型服務容器使用 GPU。
:::

## 4. 三種 GPU 配置需求

| 情境 | 配置例子 | 需要呈現的結果 |
|---|---|---|
| 整張 GPU 分配 | Container A 用 GPU 0，B 用 GPU 1 | 各容器指派的 GPU 與占用 |
| 單張 GPU 共享 | Container A、B 共用 GPU 0 | 共享關係、用量及支援限制 |
| 單一 Container 跨多卡 | Container A 使用 GPU 0、GPU 1 | 容器取得多卡，模型實際跨卡運行 |

**共同需求：能看見分配、使用狀態與資源衝突。**

:::notes
三種皆為明確需求。整卡分配是資源指派與占用管理，不直接等於硬體安全隔離。共享的限制與保證依硬體和方案驗證。多卡需分開驗證容器可見性與模型服務實際使用能力。
:::

## 4. 情境 A：雙 GPU 跑一個大模型

1. 查看單機資源總覽，確認兩張 GPU 可用。
2. 建立模型服務 Container，選擇 GPU 0 與 GPU 1。
3. 套用經驗證的模型跨卡設定，啟動服務。
4. 送出測試請求，查看結果與兩張卡的實際使用。

**驗收：Container 能使用兩張卡，且模型服務確實利用多卡完成推論。**

:::notes
容器可見多卡不等於模型自動分散。需驗證模型平行化、硬體連線、可用記憶體及相容性。尚未指定模型與效能門檻，不承諾所有模型可跨卡或效能提升倍數。
:::

## 4. 情境 B：同機運行多個工作

| 配置 | 操作情境 | 驗證重點 |
|---|---|---|
| 整卡分開 | 模型 A 使用 GPU 0，B 使用 GPU 1 | 指派結果與實際使用一致 |
| 同卡共享 | 兩個工作共用 GPU 0 | 同時運行，觀察記憶體與資源競爭 |
| 異常處理 | 新工作超過可用資源 | 提示衝突，可停止工作及恢復 |

**共享不等於固定比例切割。** 產品需標示可提供的限制、隔離與適用硬體。

:::notes
不在此指定 MIG、MPS 或其他共享方案，也不以 CPU／RAM 容器限制類推 GPU 可任意分割。產品需區分整卡占用衝突與允許共享的情境。GPU 型號、資源限制與效能互擾要一起測試。
:::

## 4. 情境 C：匯入客戶自製 Agent

1. 客戶將自行開發的 Agent 包裝成 Docker image。
2. 匯入或取得映像，填入執行設定。
3. 設定模型連線、環境變數、連接埠與資料掛載。
4. 按需要配置 CPU、RAM 與 GPU，啟動並查看日誌。

**驗收：依接入規則部署、成功呼叫模型，停止與重啟後結果符合設定。**

:::notes
映像 registry 取得與檔案匯入是否皆列首版需估工。需定義執行參數、健康檢查、資料路徑、權限與版本責任。Agent 若只呼叫模型 API 不必直接配 GPU。容器停止不一定會取消已送到外部服務的請求，需另定管理範圍。
:::

## 4. 情境 D：選用預先整合的 Agent

| 候選環境 | 現有研究 | 產品化需完成 |
|---|---|---|
| OpenClaw | 部署、設定、工具與運行測試紀錄 | 固定版本、設定入口與功能驗收 |
| Hermes | 部署、設定、工具與運行測試紀錄 | 固定版本、設定入口與功能驗收 |

選擇環境、設定模型及工具後，開啟 Agent 使用入口。

**第一版納入清單與功能深度仍需決定，不預設兩者完全相同。**

:::notes
依據：[GitLab 全庫研究](../repository-review/index.html)。可提供專用設定頁或接入上游 Dashboard，形式待設計。NemoClaw／OpenShell 研究包裝涉及子層容器，需定義與通用 Docker 管理的對應，不假設一個普通容器即包含全部功能。
:::

## 4. 日常管理與維護旅程

| 工作 | 使用者應能完成 |
|---|---|
| 看資源 | GPU、顯示記憶體、CPU、RAM 與儲存狀態 |
| 管容器 | 清單、建立、啟停、移除及執行日誌 |
| 改設定 | 資源、變數、連接埠與掛載，知道是否需重啟 |
| 找問題 | 分辨容器、模型連線、GPU 或工具異常 |
| 做維護 | 保存設定與資料，重啟或維護後驗證恢復 |

免產品帳號操作，仍需定義管理權限與資料保留規則。

:::notes
上列為產品需求，非已交付能力。Container running 不代表推論或工具可用。移除需區分保留資料與永久刪除，開機自啟與配置恢復也需驗證。備份範圍必須列清單。
:::

## 6. GPU 配置驗收

| 配置需求 | 驗收方式 |
|---|---|
| 整卡分配 | 不同容器指派不同 GPU，確認配置與使用一致 |
| 單卡共享 | 同卡執行兩個工作，量測資源競爭、失敗與恢復 |
| 單容器跨多卡 | 可見多張 GPU，實際模型完成跨卡推論 |
| 資源衝突 | 資源不足或重複占用時顯示原因並能恢復 |

**結果需對應 GPU 型號、模型、映像及版本，明列共享的保證範圍。**

:::notes
共享除了兩個程序啟動，還需觀察記憶體不足、效能互擾及工作結束。三種需求已確認，能保證多少限制由試驗決定。多卡不預先指定效能增益。
:::

## 6. 執行階段與交付關卡

| 階段 | 主要產出 | 進入下一階段的條件 |
