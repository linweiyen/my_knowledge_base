AIDMS 在 MPS 與 MIG 之間，應該怎麼定位？

這份文件把完整對話整理成可閱讀的技術與產品說明：MPS 適合彈性共享，MIG 適合硬體隔離；AIDMS 可用 Project 作為租戶邊界，在 Project 內用 MPS 提供動態 vRAM quota，並在需要強隔離時使用 MIG 或 Dedicated GPU。

一頁結論

如果只用一句話總結：MPS 是彈性共享，不是硬體隔離；MIG 是硬體隔離，不是高度彈性；AIDMS 的價值是用 Project 與 Policy Layer 幫客戶選對模式。

建議主打

MPS Sharing Mode

同一 Project 內，多個 LLM instance 共享同一張 GPU，透過 vRAM quota 與部分 compute 控管提升 GPU 使用率。

建議補強

MIG Isolation Mode

當客戶需要硬體級隔離、固定配額、較穩定 SLA 或跨安全邊界時，用 MIG 或 Dedicated GPU。

AIDMS 定位

Project-Level Governance

Project 是主要資源與租戶邊界。MPS 不跨 Project 共享，降低跨租戶安全、稽核與故障擴散風險。

建議對外主軸：AIDMS 的 MPS 模式是在 Project 內共享 GPU，而不是跨 Project 共享 GPU；Project 作為單一租戶邊界，可有效降低跨租戶共用 MPS 的安全與稽核問題。若需要硬體級隔離，建議使用 MIG 或獨占 GPU。

12歲也懂的比喻

MPS

同一間大教室，大家一起用

MPS 像是很多學生在同一間大教室上課。老師可以規定每組最多用幾張桌子，也可以規定一次不要派太多人上台，但教室、走道、黑板、冷氣還是一起用。

意思：可以做 vRAM quota 與部分執行比例控管，但 GPU core、bandwidth、cache 還是共享。

MIG

把大教室隔成幾間小教室

MIG 像是把一間大教室用牆壁切成多間小教室。每間小教室有自己的桌子、黑板與空間。A 班再吵，也比較不會影響 B 班。

意思：提供硬體級隔離，但切好後彈性比較低。

MPS 原理

MPS，Multi-Process Service，主要目標是讓多個 CUDA process 更有效率地共用同一張 GPU。

MPS 解決什麼問題？

  • 讓多個小模型或多個推論服務同時使用 GPU。
  • 降低多 process 之間的 context switching 成本。
  • 提升 GPU utilization，避免一張大 GPU 被單一小模型閒置浪費。
  • 可搭配 memory limit 與 active thread percentage 做軟體層資源控管。

MPS 不等於什麼？

MPS 不等於 MIG。MPS 不會把 GPU 硬體真的切成多張小 GPU。它是同一張 GPU 上的共享與調度機制，不是完整硬體隔離。

MIG 原理

MIG，Multi-Instance GPU，是把支援的 NVIDIA GPU 在硬體層切成多個 GPU instance。每個 instance 像是一張小 GPU，擁有固定的 compute 與 memory 資源。

MIG 的價值

  • 硬體級資源隔離。
  • 每個 slice 有固定 vRAM 與部分硬體資源。
  • 適合多租戶、強隔離、固定 SLA、政府或金融場景。
  • 可讓管理平台把一張大 GPU 當成多張小 GPU 分配。

MIG 的限制

  • 切割 profile 有固定規格，不是想切 13GB 就切 13GB。
  • 重新變更 geometry 通常需要先停掉該 GPU 上的 workload。
  • 不適合把多個小 MIG slice 再合起來跑一個大模型。
  • 對大模型 tensor parallel / NCCL 不是最理想架構。

一堆小 LLM 推論服務，該用 MPS 還是 MIG？

推薦：Project 內 MPS Sharing

如果是同一個 Project / 同一租戶內，有很多小 LLM、embedding、reranker 或分類模型，MPS 比較便利。

  • 彈性高
  • vRAM quota 可調
  • 較容易提升 GPU utilization
  • 不需要事先切固定 MIG profile

推薦：MIG Isolation

如果是不同租戶、不同安全邊界、需要硬體隔離或固定 SLA，MIG 更合適。

  • 硬體級隔離
  • 固定配額
  • 較可預期
  • 較適合政府、金融、多租戶環境

大模型能不能跨 MIG Instance？

要分清楚：container 看得到多個 MIG device，和一個大模型能不能穩定跨它們做 tensor parallel，是兩件事。

同一張 GPU 上的多個 MIG instance

不建議把同一張 GPU 上的兩個 MIG instance 當成兩張 GPU 來跑同一個大 LLM。MIG 的設計是隔離，不是合體。

不同 GPU 上的 MIG instance

技術上可能看得到，也可能在某些環境下跑得起，但不建議把它當成正式穩定的大模型 tensor parallel 架構。

MPS vRAM Quota 與 OOM 行為

假設一張 RTX PRO 6000 96GB，在 MPS 模式下配置：LLM Instance A = 36GB，LLM Instance B = 60GB。A 超過 36GB 會怎樣？

如果 36GB 是真正生效的 MPS / CUDA hard memory limit，A 超過 36GB 時會 OOM，不會吃到 B 的 60GB。
如果只是 UI 顯示或 runtime 軟設定，沒有真正設 hard limit，A 可能吃掉共享 GPU memory pool 裡原本預期留給 B 的空間，導致 B 後續 OOM。
情境 A 超過 36GB 的結果 對 B 的影響
MPS / CUDA hard memory cap 生效 A 自己 OOM 不會侵占 B 的 quota
只有 runtime policy，沒有 hard cap A 可能繼續配置 B 之後可能 OOM
MIG A 不可能越過硬體 slice 邊界 隔離性最高

產品上可以宣稱什麼？

AIDMS 支援 LLM instance-level vRAM quota，可限制單一 LLM instance 的 GPU memory 使用上限，避免單一服務過度佔用整張 GPU。

Active Thread Percentage vs GPU Core / SM 硬體隔離

這兩者常被混淆，但差異很大。

MPS Active Thread Percentage

限制你最多派多少工作進 GPU

它是軟體層控制，像是規定某個 LLM instance 最多可以讓多少比例的工作同時活躍。

不是：固定把某幾組 SM 永遠分給這個 instance。

MIG SM Isolation

真的把 GPU 的廚師團隊分家

MIG 會把部分 SM、vRAM 與相關硬體資源切給某個 instance。這比較像固定分配小 GPU。

特性：隔離較強、效能較可預期，但彈性較低。

MPS 統一 UID / UUID 的影響

技術提到使用 MPS 時，所有使用者的 UUID 或 UID 需要統一。這通常代表多個 instance 會以同一個 Linux 使用者身份，或連到同一個 MPS server。

主要影響

  • OS-level user isolation 變弱：Linux 看到的 owner 可能都是同一個 user。
  • 稽核責任要靠 AIDMS 補：不能只靠 Linux UID 分辨是哪個客戶或 instance。
  • 檔案權限要小心：同 UID 可能有相同檔案權限，要用 container、namespace、volume 隔離。
  • 故障可能擴散：同一 MPS server 內某個 client 的 fatal fault，可能影響其他 client。
  • nvidia-smi 觀察可能不直覺：可能看到 MPS server，而不是每個 client 的清楚 attribution。
MPS 不應該被定位成跨租戶強隔離方案。若多個真正不同客戶共享同一個 MPS server，安全、稽核與故障隔離風險會變高。

AIDMS Project 作為單一租戶邊界

你們的設計是：AIDMS 有 Project，Project 底下納管完整數張 GPU，Project 視為單一租戶。這是非常關鍵的設計，可以大幅降低 MPS 的跨租戶問題。

產品定位與對外說法

建議對外說法

AIDMS 以 Project 作為資源與租戶邊界。每個 Project 可納管一組專屬 GPU pool，並在 Project 內透過 MPS Sharing Mode 讓多個 LLM instance 共享 GPU 資源。此設計可在不跨租戶共享 GPU 的前提下，提供 vRAM quota 與彈性調度能力，兼顧 GPU 使用率與租戶邊界。若需要更嚴格的硬體隔離，AIDMS 可搭配 MIG 或 Dedicated GPU 模式。

短版產品說法

AIDMS 的 MPS 模式是在 Project 內共享 GPU，而不是跨 Project 共享 GPU。Project 作為單一租戶邊界，可有效避免跨租戶共用 MPS 所帶來的安全與稽核問題；但 Project 內的 instance 仍共享 GPU core、bandwidth 與 cache，因此若需要硬體級隔離，仍建議使用 MIG 或獨占 GPU。

可以宣稱

  • AIDMS 支援 LLM instance-level vRAM quota。
  • AIDMS 可限制單一 LLM instance 的 GPU memory 使用上限。
  • MPS Sharing Mode 適合 Project 內多個小型 LLM 服務彈性部署。
  • AIDMS 可提升 GPU 使用率，避免單一小模型長時間獨占整張 GPU。
  • Project 是 AIDMS 的主要資源與租戶邊界。

避免宣稱

  • 不要說 MPS 等同 MIG。
  • 不要說 MPS 提供完整硬體級隔離。
  • 不要說可以保證每個 instance 固定 GPU core、bandwidth、cache。
  • 不要說大模型可以穩定跨多個 MIG slice 做 production tensor parallel。

建議設計規則

Rule 1：MPS Server 不跨 Project

一個 MPS server 只服務一個 Project。不要讓 Project A 與 Project B 共用同一個 MPS server。

Rule 2：GPU 不跨 Project 共享

如果 Project 是單一租戶邊界，一張 GPU 在同一時間最好只屬於一個 Project。MPS sharing 只在 Project 內發生。

Rule 3：Project 內才允許 MPS Sharing

MPS 的高彈性與 vRAM quota 優勢適合用在同一信任邊界內，例如同一客戶、同一 Project、同一組服務。

Rule 4：強隔離需求使用 MIG 或 Dedicated GPU

如果客戶要求固定 SLA、硬體級隔離、不同部門不互相影響，應提供 MIG Isolation Mode 或 Dedicated GPU Mode。

Rule 5：大模型跨卡用完整 GPU

70B / 72B / 大型 VLM / MoE 需要 tensor parallel 時，建議使用完整 GPU 跨卡，不要用多個 MIG slice 拼 production 架構。
