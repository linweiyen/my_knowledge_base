AI Coding 民間案例研究

從 MedAI、法律偵探／TW Legal RAG 出發，對照 Elora Health 與 Kbag，研究專業工作者如何把需求變成產品、AI 如何參與開發，以及從展示走向營運的條件。

查證日：2026-10-21。verified 表示已核對可取得的公開來源，不表示所有主張均已獨立驗證。MedAI 與法律偵探的 AI coding 工具仍待確認。本次未註冊帳號、提交病歷或案件資料、實測服務效能或執行第三方程式碼。

1. 核心結論與研究範圍

「產品使用 AI」與「產品由 AI 協助寫程式」是兩個問題。公開網站、GitHub、MCP 或獨立開發，都不足以直接證明 AI coding；後者需要作者說明、開發紀錄或可追溯提交。

本研究判斷：最值得複製的是「領域需求 → 小範圍產品 → 可檢查的成果 → 持續營運」。AI 可以降低實作門檻，但需求判斷、資料品質、驗收與維護責任仍需人負責。不能只憑完成網站就推論商業成功。

使用者提供的兩個法律連結屬於同一產品生態，合併分析，避免重複計數。另補入有明確 AI 開發敘事的 Elora 與 2026 年 Kbag 案例。2025 年案例用於追溯歷程，不假定目前仍有相同規模。

3. MedAI：先還原真正的工作流程

官網自稱醫療 AI 助手。本次文字擷取得到載入失敗備援頁，連往 Google Cloud Run 網域的應用；直接連結也未能透過研究工具取得內容。[S1] 這是擷取限制，不能據此宣稱所有使用者皆無法使用或服務已停止。

尚未確認：作者與職業、是否 AI coding、是否處理病歷或語音、採用模型、收費與實際場域導入。備援網址含 medical-record-optimizer，但命名不能當成已驗證功能。

研究判斷：此案要先回答「誰原本在什麼情境，花多少時間做哪件事」。若核心是文書整理，應比較它比一般聊天工具多出的流程價值；若涉及醫療判斷，須另取得相應驗證，不能以介面完成度代替成效。

建議用合成或充分去識別的資料，觀察輸入、產出、人工修改與失敗恢復；這是後續研究設計，本次未實測。

4. 法律偵探／TLR：把專業資料做成可被 AI 呼叫的能力

作者背景：黃思齊個人頁自述具律師、半導體業與軟體開發經驗，並獨力打造平台。[S4] 不宜包裝成毫無技術背景的法律人案例。關於頁自述一人維護資料管線與服務，檢索在自有伺服器、回答使用雲端模型，並明示尚未取得第三方 ISO 42001 認證。[S3] 獨力開發與 AI 寫了多少仍是不同問題。

產品分層：法律偵探網站面向使用者；TLR 面向 AI 助理；公開 CLI 連接遠端服務。README 說明檢索與生成分離，公開程式不包含後端索引，引用檢查也不能保證見解解讀正確。[S2][S5] 研究重點是資料如何交付、什麼能驗、什麼不能驗，而不只標示有 RAG。

來源一致性：TLR 首頁、GitHub 與其他官網頁面的資料量快照不同；README 有 2026-10-20 統計日。[S2][S5] 本文不把筆數視為已獨立清點的現況，也不由筆數推出檢索品質或使用量。

以下為本研究的工程推論：

  1. 把取得依據做成工具，可讓不同助理共用資料能力，減少重建整套對話介面的必要。
  2. 領域知識可轉成結果格式、引用規則與錯誤狀態，使品質要求更容易反覆驗證。
  3. 資料同步、檢索評估與維運可能才是長期成本；CLI 大小無法代表全系統建置難度。
  4. 引用查核只是其中一層防護，通過檢查不等同語意正確。

維護與授權：貢獻指南採單一作者、不接受外部 PR 的政策。[S6] 官網標示 ELv2。[S2] 本文使用「公開原始碼」，不將其等同可無條件商用或可完整自架的整套開源服務；重用前須閱讀對應版本條款。單人維護值得追蹤備援與更新能力，但現有證據不能判定可靠性好壞。

AI coding 待查：實際工具、哪些模組由 AI 初稿、人工如何審查、資料處理如何驗收、失敗如何修正。現階段定位為「專家主導的 AI 產品與工具化案例，AI coding 待證」。

5. Elora Health：從不會寫程式到早期付費驗證

Lovable 2025-01-29 訪談稱，健康／營養背景的 Tom 無程式經驗，用 Lovable 約一個月完成應用，採對話迭代、即時預覽與 GitHub 版本管理；曾因 AI 修改破壞功能而回復版本，當時有兩位付費客戶。[S7] 這支持早期產品敘事，尚不足以代表穩定獲利、今日營運規模或醫療有效性。

研究判斷：參考價值在將專業需求轉成日常互動，並用預覽與回饋縮短迭代。不可只複製「一個月」：學習、返工與維護也要計入。初版能跑與持續可維護，是兩個驗收階段。

可借鏡方法：一次完成一段使用者旅程，留下可運作版本，再改下一段；修改持續擴大錯誤時，回到前版並重述問題。這是本文提煉的流程建議，工具不限 Lovable。

6. Kbag：2026 年實體營運整合案例

Lovable 2026-09-10 案例稱，土木業者 Kedde 與技術夥伴用 Lovable 約三週、約 500 美元平台費完成首版，串接 Volvo Connect 車隊資料，以地址與即時條件支援物流與報價；2026 春季上線，三個月由一車增至五車。[S8] 這些屬供應商刊載訪談，未經本研究獨立財務或營運查核。

技術夥伴參與，不宜簡化成業者一人純靠提示完成複雜演算法。500 美元也不能當成人工、車隊、地圖、外部 API 與維運的總成本。車輛增加並非軟體單獨造成的因果證據。

研究判斷：價值在串起訂單、車輛狀態與日常決策。企業可優先找原本靠電話、試算表與人腦協調的交接點，再評估 AI coding 能否降低整合成本。營運資料與規則品質，仍決定軟體能否幫上忙。

8. 用對照研究校正「一定變快」的敘事

METR 2025-07-10 發表實驗，針對 16 位熟悉自身大型開源專案的開發者、246 項任務，觀察到允許使用當時 AI 工具後平均多花 19% 時間。[S9] 這是特定族群、任務與時期，不能外推到新手新建應用或 2026 年所有工具。

METR 2026-02-24 更新指出，後續研究受到參與者與任務選樣、多代理工時計算等影響，難以可靠估計加速幅度，並認為工具可能已比早期更有幫助。[S10] 因此不能將舊結果當成今日定論，也不能以供應商案例推導人人十倍速。

研究建議：分開衡量「原本做不出來，現在做得出來」與「相同品質下節省工時」。前者評估能力擴張，後者需相近任務基線。付費、留存、品質與維護成本是另外的證據，不能互相代替。

9. 下一步深挖與訪談清單

以下為建議研究計畫，本次未聯繫作者或執行訪談。

  1. 優先補 MedAI 的作者與公開示範；先還原工作流，避免以名稱猜測功能。
  2. 法律偵探追查開發工具與過程，把一人開發拆成資料、應用、測試、部署與維護五段。
  3. Elora 追查案例之後的留存與維護；Kbag 追查總成本、異常訂單與人工介入。
  4. 後續優先收錄作者可識別、流程可追溯、成果可觀察的作品，不以聲量與畫面漂亮判定成熟。
訪談問題 希望取得的證據
原本誰做什麼，既有工具為何不夠？ 原流程、痛點、輸入與輸出
AI 寫哪些部分，人改哪些？ 一個真實功能的提示、修改與驗收紀錄
從首版到能用，返工最多在哪？ 失敗版本、bug 與修復時間
工期是否包含學習、部署與資料處理？ 分階段工時與非平台支出
上線後誰負責故障與更新？ 維護紀錄、備援與更新流程
有多少人重複使用、願意付費？ 去識別留存、使用與收入證據

若自行做對照實驗，建議以小工作流開始：先寫出輸入、輸出、錯誤與驗收條件；記錄實作、審查、除錯、部署總時間；再修改一次真實需求，觀察可維護性。敏感領域先用合成資料。以上是評估建議，並非已完成實測。
