一、執行摘要

01

Prompt engineering 沒有消失，但已不夠

Prompt engineering 處理「怎麼問」。它仍然重要，但當任務變成多步驟、需要查資料、呼叫工具、寫檔案、檢查結果時，單靠 prompt 會把太多責任壓在一段文字上。

02

Context engineering 是資訊供給架構

Stanford CS224G 將 context engineering 視為比 prompt 更大的問題：模型在生成前到底看見哪些 system instruction、history、tools、RAG、user data 與最後 prompt。

03

Harness engineering 是外層執行基座

Harness engineering 再往外一層，設計模型周圍的 runtime：任務規格、context selection、tools、permissions、memory、verification、observability、human approval 與 completion criteria。

一句話定義：AI Harness Engineering 是把 AI 從「會回答的模型」變成「可安全執行、可驗證完成、可觀測與可治理的任務系統」的工程實踐。

二、什麼是 Harness Engineering？

「Harness」原意是馬具或安全帶，也可指測試或執行某個系統的支撐裝置。在 AI agent 語境裡，harness 是模型外面的工程層：它提供任務、上下文、工具、記憶、沙箱、權限、驗證與觀測。換句話說，模型是推理核心，harness 是讓它可靠工作的作業環境。

層級關注問題典型產物失敗時會發生什麼
Prompt Engineering如何寫出清楚、可預期的指令？system prompt、user prompt、few-shot examples格式跑掉、理解錯任務、回覆泛泛而談
Task Briefing任務本身是否說清楚？背景、目標、限制、輸入、完成定義模型做了看似合理但不是你要的事
Context Engineering模型這一回合應該看到哪些資訊？compiled context、RAG snippets、tools schema、history summary拿錯資料、漏資料、token 爆掉、被舊資訊誤導
Harness Engineering整個 agent 如何安全、可驗證地執行任務？orchestrator、tool gateway、policy engine、verifier、trace提早宣告完成、亂呼叫工具、無法追查錯誤、權限外洩

因此，harness engineering 不等於「寫更長 prompt」。它更像是在做一套 AI 任務執行平台：先把任務定義清楚，再建構上下文，再讓模型做推理與工具選擇，最後用外部機制判斷是否真的完成。

三、Stanford 的五個 Context Engineering 槓桿，與你記得的五個查核點

Stanford CS224G Lecture 6 的核心概念是：不要只調 prompt，而要工程化模型周圍的輸入。該教材提出 application builder 可以控制的五個 levers：

1. Personas / Custom Instructions

定義角色、語氣、長期偏好與不可覆寫的高層規則。

2. Available Tools

定義模型可呼叫哪些工具、何時呼叫、參數格式與風險邊界。

3. RAG / Datastore Connections

定義模型如何取得外部知識、企業文件、資料庫或搜尋結果。

4. User-Submitted Data

處理使用者上傳檔案、圖片、表格、程式碼與當前任務資料。

5. Your Prompt

最後一層任務指令，負責明確提出本次要完成的事。

關鍵句

Don’t just tweak the prompt. Engineer the inputs that surround it.

四、生產級 AI Harness 架構

這個架構把 AI 任務分成四段：Brief 定義要做什麼，Context 決定模型看見什麼，Orchestration 決定模型與工具如何互動，Verification 決定是否真的完成。

type Brief = {
  background: string;
  goal: string;
  constraints: string[];
  resources: string[];
  definitionOfDone: string[];
};

async function runAgent(userInput: string, userId: string) {
  const brief = await compileBrief(userInput);
  const context = await buildContext({
    brief,
    persona: await loadPersona(userId),
    history: await summarizeHistory(userId),
    retrieved: await retrieveDocuments(brief.goal),
    tools: selectTools(brief.goal)
  });
  const step = await model.respond({ brief, context });
  const result = await executeOrRespond(step);
  return verifyAgainstDefinitionOfDone(result, brief.definitionOfDone);
}

五、核心元件與工程模式

1. Task Specification / Brief Compiler

把模糊需求轉成可執行規格。這一層最常被忽略，卻最容易造成 agent 做錯方向。

好 brief 背景、目標、限制、輸入、完成定義都明確。
壞 brief 只有「幫我做一下」或「整理一下」，沒有邊界與驗收。

2. Context Selection / Context Builder

決定每一回合要放入哪些 system instructions、歷史摘要、RAG 結果、附件、工具 schema。重點不是塞滿 context window，而是高訊號、低噪音。

3. Tool Gateway / Permission Layer

工具讓 agent 可以查資料、寫檔、呼叫 API、發送通知。但所有有副作用的工具都應有 policy gate、scope check、human confirmation 或 sandbox。

4. Verification / Definition of Done

「完成」不應由模型自稱，而應由外部測試、schema validation、groundedness evaluator、LLM judge 或 human sign-off 判定。

5. Observability / Trace

生產系統必須知道每次 run 的 prompt/context 版本、檢索來源、工具呼叫、token cost、latency、錯誤與人工介入紀錄。

ai_task_brief:
  background: "目前情境、使用者、系統或文件脈絡"
  goal: "這次要達成的具體結果"
  constraints:
    - "不可違反的格式、安全、法規或業務限制"
  resources:
    - "可使用的資料、文件、API、工具"
  definition_of_done:
    - "輸出需包含哪些內容"
    - "需要通過哪些測試或驗證"
    - "何時需要人類確認"

六、案例研究

OpenAI Codex：Harness Engineering 的代表案例

OpenAI 在 Codex 相關文章中明確使用「harness engineering」語彙，說明在 agent-first 開發中，工程師的角色從直接寫每一行程式，轉向建構 repo knowledge、tests、lints、invariants、review loops 與可讀的 agent environment。這說明 coding agent 的能力不只取決於模型，也取決於周圍的 harness 是否讓模型看得懂、改得動、驗得過。

Spotify Honk：Context Engineering + Verification Loops

Spotify 的 background coding agent 經驗顯示，早期讓使用者手動挑選 context 很容易失敗；後來透過更好的 context engineering、verifier loop、LLM judge 與 sandbox，讓 agent 能處理大規模 PR。這裡的關鍵不是更花俏的 prompt，而是 context 與 done criteria 外部化。

Air India AI.g：企業客服 Agent

Air India 使用 Azure OpenAI、RAG、企業系統整合與內容安全，打造能處理大量客服問題的虛擬助理。這種系統的核心不是聊天，而是把檢索、資料庫、API、安全與升級流程整合為完整 harness。

POSCO / Repo Prompt：把 Context Builder 獨立出來

POSCO 與 Repo Prompt 的案例都顯示，先讓一個 context-building process 整理大量文件或程式庫，再交給 reasoning model 深度分析，是提升品質與降低成本的重要模式。

七、可落地 Harness Engineering 檢核表

檢查項要問的問題最低可接受狀態常見失敗訊號
背景模型是否知道任務脈絡、使用者角色、資料範圍？有明確背景與 scope回覆泛化、忽略企業脈絡
目標這次任務是否能用一句話說清楚？有單一主要目標與輸出型別模型自行擴張任務範圍
限制哪些格式、安全、權限、商業規則不可違反？限制放入 system / policy 層格式跑掉、越權工具呼叫
資源可用哪些文件、工具、API、資料庫？資源白名單與最小權限檢索錯誤、工具過多、資料污染
完成定義什麼外部條件成立才算完成？有 verifier / grader / human approval模型提早宣告成功
觀測是否能追蹤每次 run 的上下文、工具、成本與錯誤？有 trace ID 與 dashboard錯誤不可重現、成本暴衝
實務建議：先從 Task Briefing Checklist 開始，把「背景、目標、限制、資源、完成定義」標準化；接著建立 context builder；最後才導入 tool gateway、verifier、trace 與 policy engine。這樣可以避免團隊一開始就陷入 agent framework 選型，而忽略真正決定品質的任務與上下文設計。
