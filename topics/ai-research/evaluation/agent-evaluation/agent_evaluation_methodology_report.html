1. 執行摘要

一句話結論：Agentic AI 的 Evaluation 不只是「看答案對不對」，而是要同時看 任務有沒有完成、過程是否合理、工具是否用對、是否安全、是否穩定、成本與延遲是否可接受。

如果把 agentic AI 粗略說成「LLM + Agent + Evaluation」，方向上大致正確，但更精準的說法是： LLM 是能力來源，Agent 是把能力接上工具、記憶與流程的執行系統，而 Evaluation 是貫穿設計、測試、上線、監控與改版的量測系統。

對高中生來說，可以把 Agent Evaluation 想成「考試不只看最後答案，也看解題步驟、工具選擇、是否作弊、是否穩定、是否花太久」。一個 AI Agent 就像一個會自己做事的學生：它可能會查資料、按網頁、寫程式、呼叫 API、請其他子 Agent 幫忙。這種系統一旦做錯，錯誤可能不是最後一句話才發生，而是前面某一步就走歪了。

結果層

任務最後有沒有完成？答案正不正確？資料狀態是否變成目標狀態？

過程層

中間每一步是否合理？工具有沒有用對？是否有錯誤傳遞或繞圈？

營運層

是否安全、穩定、便宜、快速？上線後是否退化？能不能被監控與修正？

2. 為什麼 Agent Evaluation 重要

傳統聊天機器人多半只是「回答一句話」。但 Agentic AI 的目標是「完成任務」：例如幫客戶查訂單、修改資料庫、寫程式、整理報告、操作瀏覽器、安排流程。這代表 Agent 不只會說話，還會做動作。

一旦 AI 會做動作，Evaluation 就變得更重要，原因有四個：

原因高中生版解釋實務風險
Agent 是多步驟系統 像解一道複雜數學題，中間一步錯，最後可能全錯。 只看 final answer，可能不知道錯在哪一步。
Agent 會使用工具 像學生會用計算機、查字典、上網，但可能拿錯工具。 查錯 API、傳錯參數、誤刪資料、誤觸高風險操作。
Agent 輸出不穩定 同一題考十次，它可能有時對、有時錯。 Demo 很漂亮，但上線後表現飄忽不定。
Agent 有安全風險 別人可以在網頁或文件裡偷塞指令，騙它做不該做的事。 Prompt injection、資料外洩、越權工具呼叫。

3. 和傳統 LLM Evaluation 的差異

比較項目傳統 LLM EvaluationAgent Evaluation
評估對象 主要看模型的輸出文字。 看模型、工具、記憶、流程、環境互動的整體行為。
成功標準 答案是否正確、是否符合格式、是否安全。 任務是否完成、每一步是否合理、工具是否用對、成本是否可接受。
資料型態 Prompt、Answer、Reference。 Prompt、Trace、Tool calls、Environment state、Final result。
常見問題 幻覺、格式錯、答非所問。 規劃錯、工具錯、參數錯、循環、越權、記憶錯、成本爆炸。
評估方式 Exact match、Rubric、LLM-as-judge、人類評審。 以上都要，加上 trajectory eval、tool eval、sandbox eval、production monitoring。
比喻：傳統 LLM Evaluation 像批改作文；Agent Evaluation 像評估一個學生能不能完成科展專題。 你不只看最後報告，還要看他查資料、做實驗、用工具、記錄結果、處理錯誤的整個過程。

4. 常見評估層級

一個成熟的 Agent Evaluation 通常不是單一測驗，而是多層次評估。

層級要問的問題常見指標
最終答案 / 任務結果 最後有沒有完成任務？答案是否正確？ Success rate、Exact Match、Pass@k、State diff
過程 / Trajectory 中間路徑是否合理？哪一步開始錯？ Step accuracy、Trajectory score、Root-cause rate
工具使用 工具有沒有選對？參數有沒有填對？ Tool-name accuracy、Argument match、Schema validity
規劃能力 Agent 是否會拆任務、安排順序？ Plan validity、Subtask completion、Replanning success
記憶能力 多輪任務中是否記得重要資訊？ Memory recall、Memory precision、Contradiction rate
可靠性 / 穩定性 同一任務跑多次是否穩定？會不會繞圈？ Variance、Loop rate、Retry rate、Pass^k
安全性 遇到惡意輸入是否失控？會不會洩密？ Attack success rate、Leakage rate、Safe refusal rate
成本與延遲 完成一次任務花多少錢、多少時間？ Cost/task、Token/task、p50/p95 latency、Tool call count

6. 詳細方法解析

6.1 自動化任務成功率

這是最直覺的方法：給 Agent 一個任務，最後看它是否完成。像是：「幫我查 C1024 客戶在 2026-06-01 的訂單」，最後資料是否正確、狀態是否符合預期。

常見做法是建立一批測試任務，每題都有標準答案或可驗證的目標狀態。Agent 跑完後，用程式比對結果。GAIA、WebArena、SWE-bench、τ-bench 這類 benchmark 都屬於這一大類，只是任務類型不同。

常見陷阱：只看最後答案可能不知道錯在哪裡。Agent 可能中間亂做，最後剛好猜對；也可能答案看起來對，但資料庫狀態其實被改錯。

6.2 步驟級評估 / Trajectory Evaluation

Agent 的完整執行紀錄稱為 trace 或 trajectory。這裡面包含它每一步想做什麼、呼叫什麼工具、工具回傳什麼、接下來怎麼決定。

這種方法像老師批改數學題的「解題過程」。即使最後答案錯了，也能知道是公式用錯、單位換錯，還是最後計算錯。對 Agent 來說，這能幫助我們判斷是規劃錯、工具選錯、參數錯，還是模型理解錯。

要看什麼例子
規劃是否合理是否先查訂單，再判斷退款資格，而不是直接退款。
工具是否正確是否呼叫 lookup_order，而不是 delete_order。
參數是否正確customer_id、日期、產品名稱是否填對。
錯誤是否恢復API 失敗後是否重試或改問使用者，而不是瞎編。

6.3 工具呼叫正確性

Tool use 是 Agent 與一般 LLM 最大的差異之一。Agent 不只要會回答，還要會「選工具」與「填參數」。 

{
  "tool": "lookup_customer_order",
  "arguments": {
    "customer_id": "C1024",
    "order_date": "2026-06-01"
  }
}

評估時至少要拆成兩層：第一，工具名稱是否正確；第二，工具參數是否正確。更進一步還可以看 schema 是否合規、是否過度呼叫工具、工具失敗後是否能恢復。

6.4 模擬環境 / Sandbox Evaluation

如果 Agent 會操作瀏覽器、作業系統、程式碼或資料庫，最好不要直接讓它在真實環境亂跑，而是先放進 sandbox。這就像學開車先在駕訓場，不是馬上上高速公路。

WebArena 讓 Agent 操作模擬網站，OSWorld 讓 Agent 操作真實作業系統環境，SWE-bench 讓 coding agent 在容器裡修改真實 GitHub issue 並跑測試。這些方法都強調「可重現」與「可驗證」。

6.5 LLM-as-Judge

有些任務很難用 exact match 評分。例如客服回覆是否有禮貌、摘要是否完整、研究報告是否清楚。這時可以用另一個 LLM 當評審，依照 rubric 打分。

注意：LLM-as-Judge 很有用，但不是萬能。Judge 也可能偏心、受提示影響、對專業領域判斷不準。因此高風險任務仍要用人類專家校準。

6.6 Human Evaluation

人類評估最貴，但在很多場景不可取代。特別是醫療、法律、金融、政府、客服品牌語氣、企業知識這些場景，最後需要專家確認標準。

實務上常見做法是：先用自動 grader 快速篩選，再把低分、分歧、高風險或抽樣案例送給人類評審。這樣可以兼顧成本與品質。

6.7 Red Teaming 與安全評估

Agent 會接觸外部資料，所以容易受到間接 Prompt Injection。惡意指令可能藏在網頁、文件、Email、工具回傳結果中，騙 Agent 忘記原本任務，或執行越權操作。

安全評估要測：是否洩漏機密、是否誤信外部指令、是否越權呼叫工具、是否拒絕合法請求、是否需要人類確認高風險動作。

6.8 回歸測試與線上監控

Agent 系統最怕「改好一個地方，壞掉三個地方」。所以每次改 prompt、換模型、改工具 schema、調 workflow，都應該跑 regression tests。

上線後也不能停止評估。真實使用者會問出測試集沒有的問題，因此 production traces 要持續抽樣、評分、警示與回流到資料集。

6.9 成本、延遲與資源評估

一個 Agent 成功率高但每次要花 3 分鐘、100 次工具呼叫、很高 API 費用，仍可能無法商用。因此每個任務都應該同時記錄 cost/task、token/task、p50/p95 latency、tool call count、retry count。

7. 實務 Pipeline 範例

7.1 客服 Agent 評估 Pipeline

客服 Agent 最常見的風險是：看起來回答得很好，但其實違反政策、查錯訂單、該轉真人卻沒轉真人。因此要同時評估任務成功率、政策合規、工具使用、人類抽查與線上監控。

flowchart TD A[蒐集客服案例與政策規範] --> B[建立離線資料集] B --> C[定義成功條件
是否解決問題 / 是否合規 / 是否該轉真人] C --> D[建立自動 graders
最終回覆 / 政策合規 / 工具名稱與參數] D --> E[在 mock 或 sandbox 工具上重跑] E --> F[抽樣送人工審查] F --> G[修 prompt / tool schema / routing] G --> H[CI 回歸測試] H --> I[小流量上線] I --> J[線上監控與告警
低分 trace 進 review queue]

7.2 資料查詢 / 工具使用 Agent 評估 Pipeline

這類 Agent 適合把「工具名稱」與「參數」拆開評估，因為很多錯誤不是模型不懂，而是查錯表、填錯欄位、日期格式錯。

flowchart TD A[建立查詢任務集
問題 / 可用工具 / 正確答案 / 正確 tool call] --> B[單步評估] B --> C[工具名稱是否正確] B --> D[參數是否正確] C --> E[執行工具並驗證最終答案] D --> E E --> F[記錄 trace] F --> G[分析失敗類型
選錯工具 / 參數漏填 / 單位格式錯] G --> H[修 schema / few-shot / routing rules] H --> I[回歸測試] I --> J[線上抽樣監控]

7.3 Coding Agent 評估 Pipeline

Coding Agent 不只要看測試有沒有過，也要看 patch 是否安全、是否只是鑽測試漏洞、成本是否合理。

flowchart TD A[蒐集 issue / spec / repo snapshot] --> B[建立容器化測試環境] B --> C[Agent 產生 patch] C --> D[套用 patch] D --> E[執行單元測試與整合測試] E --> F[執行靜態分析與安全檢查] F --> G[量測成本與延遲] G --> H[人工審查高風險 diff] H --> I[加入回歸資料集] I --> J[比較新舊 agent / prompt / model]

9. 導入開發生命週期的建議

最重要的最佳實務是：把 evaluation 當工程系統，不要當 demo 後面的附錄。 Agent Evaluation 應該從專案第一天就設計，而不是等上線前才補。

開發階段最少必做 Evaluation產出物
問題定義 定義成功條件、失敗類型、風險類型 Eval objective、Failure taxonomy、Risk map
原型期 小型離線資料集、最終成功率、單步工具評估 Dataset、Grader、Baseline
整合期 Sandbox、Trace grading、對抗案例 可重現測試環境、Trace rubric
上線前 Regression tests、A/B 比較、專家人審 Release gate、Pairwise report、批准清單
上線後 Online evaluators、Dashboard、Alerts、資料回流 線上品質儀表板、告警規則、持續更新的 eval set

建議的 Dashboard 四大區塊

品質

總成功率、分場景成功率、tool accuracy、step accuracy、human pass rate。

安全

Prompt injection 攻擊成功率、越權工具呼叫率、敏感資訊洩漏率、誤拒率。

穩定

Pass@k、重試率、循環率、長任務後段延遲、記憶錯誤率。

效率

p50/p95 latency、cost/task、token/task、步數、工具呼叫數。

回歸

新舊版本差異、失敗類型變化、改 prompt 後哪些任務變好或變差。

人審

低分 trace、使用者差評、高風險操作與專家審查結果。

10. 開放問題與限制

10.1 Benchmark 分數不等於產品可靠度

公開 benchmark 很適合比較能力，但不代表你的企業場景一定有效。Agent 可能在 GAIA 或 WebArena 表現不錯，卻在你的 ERP、客服政策、內部文件格式上失敗。

10.2 LLM-as-Judge 需要校準

LLM-as-Judge 可以快速擴大評估規模，但它本身也可能偏誤。實務上應該用人類標註資料校準 judge，並定期抽查。

10.3 Step-level Evaluation 成本較高

步驟級評估很有價值，但要標註或設計 rubric，比只看最後答案更花時間。建議先針對高風險節點做，例如 routing、tool selection、final verification。

10.4 長任務與記憶仍然很難測

很多 Agent 在短任務中看起來很好，但任務一長就會失憶、繞圈、成本爆炸。長期穩定性與記憶評估仍是快速發展中的領域。

10.5 安全測試不可能一次完成

Prompt injection、工具濫用、資料外洩、越權操作會隨著產品變化而改變。安全評估必須持續更新，不是上線前跑一次就結束。

最後總結：成熟的 Agent Evaluation 一定是混合式的。 你需要黑箱總分看任務有沒有完成，需要白箱 trace 找錯在哪一步，需要人類評估對齊真實需求，需要對抗測試看最糟情況，需要線上監控防退化，也需要成本與延遲指標判斷能不能商用。
