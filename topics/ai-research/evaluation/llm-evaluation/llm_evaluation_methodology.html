Methodology · LLM Evaluation

驗證 Fine-tuned LLM 的方法論

以法律案件分類為例 ── 雙層評估架構的設計與實作

2026 · 技術備忘錄
摘要

Fine-tune 一個 LLM 來判斷法律案件違反哪些法規後，如何驗證它真的有學到東西？常見直覺是「再找一個 LLM 來當評審」，但若把標準答案直接告訴評審 LLM，會引入嚴重的判斷偏差。本文提出一個雙層評估架構：Layer A 用程式比對結構化輸出（法條清單），Layer B 用 blind 模式的 LLM-as-judge 評估推理品質，並參考 Claude Code 的 skill-creator grader 設計，給出可直接套用的 Python 實作與 prompt template。

背景與動機

場景是這樣的：手上有約 100 個法律案件作為訓練資料，每個案件都標註了「違反哪些法規」作為標準答案。我們把這些資料拿去 fine-tune 一個 LLM，希望它能對新案件做出同樣的判斷。

問題是：怎麼知道 fine-tune 之後的模型到底好不好？

單純看 training loss 不夠 — 它只反映模型對訓練資料的擬合程度，看不出泛化能力。人工逐一審查不可行 — 規模太大且不可重現。一個自然的想法是「用另一個 LLM 來當評審」，這在學術界叫做 LLM-as-judge。

但這個方法用錯，會比沒驗證還危險：它會給你一份「看起來嚴謹」的報告，分數看起來很合理，但實際上失真。本文要解決的，就是怎麼設計這套評估流程才不會被自己騙到。

三個常見錯誤做法

在介紹建議架構之前，先列出三個非常容易踩到的坑。這些做法都來自直覺，但每一個都會讓驗證結果失真。

問題 01把標準答案先告訴評審 LLM

最常見的直覺：「把案件、模型回覆、標準答案一起丟給評審 LLM，請它判斷模型的回覆對不對。」這個流程有個致命缺陷 — 評審 LLM 一旦看過標準答案，就會傾向認為「跟標準答案像的就是對的」。它不是在獨立判斷，而是在做相似度檢查。在心理學上這叫 anchoring bias，在 LLM 評估文獻裡也有大量論文討論。

更可怕的是這種偏差很難察覺 — 分數看起來合理（因為模型輸出常常確實跟標準答案相似），但你失去了發現「模型推理薄弱但結論碰巧對」這類問題的能力。

問題 02用 LLM 評估結構化輸出

如果模型輸出包含「違反法規清單」這種可枚舉的結構化資料，用程式做集合比對就好，不必動用 LLM。Precision、Recall、F1 這些指標客觀、可重現、便宜、快速，又不會有 LLM 的隨機性。

LLM-as-judge 應該保留給「推理過程是否合理」、「自然語言摘要的品質」這類程式判斷不了的部分。把每件事都丟給 LLM 評，是浪費，而且引入不必要的雜訊。

問題 03把驗證資料寫進 Skill 裡

Skill 是給 LLM 使用的「操作手冊」，主要用途是在執行時提供指示。把驗證資料集（案件 + 標準答案）整包塞進一個 skill 雖然技術上行得通，但跟業界標準的評估流程不對齊。

標準做法是把 ground truth 放在獨立的資料檔（JSONL 或 CSV），skill 或 prompt 只用來描述「評估標準」（rubric）。資料跟邏輯分離，方便維護、擴充、版本控制。

Claude Code 的評估參考

Anthropic 為 Claude Code 設計的 skill-creator 工具有一個完整的 evaluation 架構，值得借鏡。它的核心流程是：

  1. Eval set：每個 test case 包含一個 prompt 跟一串具體的 expectations（assertions）。
  2. Executor subagent：執行模型，產生 transcript 跟 output files。
  3. Grader subagent：讀取 transcript 跟 outputs，對每個 expectation 給 PASS 或 FAIL，並引用具體文字當證據。
  4. Variance analysis：同一個 input 跑三次，看穩定度。
  5. Train/test split：60/40 分割，避免 overfit 到「改 prompt 用的那批」測試案例。

幾個值得學的關鍵設計：

  • No partial credit：每個 assertion 只能是 PASS 或 FAIL，沒有 1–5 分這種尺度。簡化判斷，提高一致性。
  • Evidence-based：要求 grader 引用具體文字，不能只說「我覺得對」。這擋掉大部分的氛圍判斷。
  • Grader 同時 critique assertions：grader 不只判斷模型輸出，還會回頭挑剔測試本身 — 例如指出「這個 assertion 太寬鬆，瞎掰的輸出也會過」。這擋掉「測試項目本身有問題」的假陽性。

雙層評估架構

結合上述教訓，我們把評估拆成兩層平行進行：一層用程式，一層用 LLM，各管各的擅長領域。

Figure 1 ── 雙層評估流程。Ground truth 只供 Layer A 比對使用；Judge LLM 在 blind 模式下獨立判斷推理品質。

為什麼分兩層？

因為「答對」跟「推理對」是兩件事，而且需要的驗證方法不同。

  • 答對（模型該講的法條有沒有講到、不該講的有沒有亂講）是個集合比對問題。它有明確答案，最適合用程式驗證 — 這就是 Layer A。
  • 推理對（從事實到結論的邏輯是否成立、有沒有遺漏爭點）是個品質判斷問題。它需要語意理解，最適合用 LLM 驗證 — 這就是 Layer B。

關鍵設計是：ground truth 只進 Layer A，不進 Layer B。這樣 Judge LLM 在判斷推理品質時，是真的在獨立思考，而不是在跟答案比對。

Layer A 實作：程式比對

Layer A 是純程式邏輯，沒有 LLM 介入。核心三步：抽法條 → 標準化 → 算集合分數。

核心程式碼

import re
from dataclasses import dataclass
from collections import Counter

# ════════════════════════════════════════════════════════════
# Step 1: 把法條從文字裡抽出來
# ════════════════════════════════════════════════════════════
# 處理常見變體：
#   "公平交易法第19條"
#   "公平交易法§19"
#   "公平交易法 第 19 條第 1 項"
# 統一變成: "公平交易法§19" 或 "公平交易法§19§1"

ARTICLE_PATTERN = re.compile(
    r"([\u4e00-\u9fff]+法)"          # 法規名稱
    r"\s*"
    r"(?:第\s*)?(\d+)\s*條"          # 第 X 條
    r"(?:\s*第\s*(\d+)\s*項)?"       # 可選的第 X 項
)

def normalize_article(law, article, section=None, include_section=False):
    """把單一法條變成 canonical 形式"""
    base = f"{law.strip()}§{int(article)}"
    if include_section and section:
        base += f"§{int(section)}"
    return base

def extract_articles(text, include_section=False):
    """從一段文字裡抽出所有法條，回傳 set"""
    matches = ARTICLE_PATTERN.findall(text)
    return {
        normalize_article(law, art, sec, include_section)
        for law, art, sec in matches
    }

# ════════════════════════════════════════════════════════════
# Step 2: 算單一案件的 Precision / Recall / F1
# ════════════════════════════════════════════════════════════

@dataclass
class CaseMetrics:
    case_id: str
    tp: set      # 模型講對的法條
    fp: set      # 模型多講的（誤報）
    fn: set      # 模型漏掉的
    precision: float
    recall: float
    f1: float

def score_case(case_id, predicted, gold):
    tp = predicted & gold
    fp = predicted - gold
    fn = gold - predicted

    precision = len(tp) / len(predicted) if predicted else 0.0
    recall    = len(tp) / len(gold)      if gold      else 0.0
    f1 = (2 * precision * recall / (precision + recall)
          if (precision + recall) else 0.0)

    return CaseMetrics(case_id, tp, fp, fn, precision, recall, f1)

# ════════════════════════════════════════════════════════════
# Step 3: 跑整個 test set + 統合
# ════════════════════════════════════════════════════════════

def evaluate_dataset(test_cases, include_section=False):
    results = []
    for tc in test_cases:
        predicted = extract_articles(tc["model_output"], include_section)
        gold = set(tc["gold_articles"])
        results.append(score_case(tc["case_id"], predicted, gold))

    # Macro average（每個 case 權重一樣）
    n = len(results)
    return {
        "per_case": results,
        "macro_precision": sum(r.precision for r in results) / n,
        "macro_recall":    sum(r.recall    for r in results) / n,
        "macro_f1":        sum(r.f1       for r in results) / n,
    }

# ════════════════════════════════════════════════════════════
# Step 4: 失敗案例分析（最有用的部分）
# ════════════════════════════════════════════════════════════

def failure_analysis(results):
    """看模型常漏哪些法條、常多講哪些法條"""
    most_missed = Counter()
    most_hallucinated = Counter()

    for r in results:
        most_missed.update(r.fn)
        most_hallucinated.update(r.fp)

    return {
        "top_missed":       most_missed.most_common(10),
        "top_hallucinated": most_hallucinated.most_common(10),
        "perfect_cases":    [r.case_id for r in results if r.f1 == 1.0],
        "zero_cases":       [r.case_id for r in results if r.f1 == 0.0],
    }

使用範例

test_set = [
    {
        "case_id": "001",
        "model_output": "本案 A 公司違反公平交易法第19條，並涉及個人資料保護法§20。",
        "gold_articles": ["公平交易法§19", "個人資料保護法§20"]
    },
    {
        "case_id": "002",
        "model_output": "違反公平交易法第25條，民法第184條。",
        "gold_articles": ["公平交易法§25"]   # 模型多講了民法§184 → FP
    },
]

summary = evaluate_dataset(test_set)
print(f"Macro F1: {summary['macro_f1']:.3f}")

analysis = failure_analysis(summary['per_case'])
print("最常漏掉的法條:", analysis['top_missed'])
print("最常瞎掰的法條:", analysis['top_hallucinated'])

設計選擇

01

比對粒度

include_section=False（預設）只比對到「條」級別；include_section=True連「項」都要對。依資料標註粒度決定。

02

Macro vs Micro

Macro：每個案件先算 F1 再平均，權重相等。Micro：先加總所有 TP/FP/FN 再算 F1。實務上兩個都報。

03

結構化輸出優先

能控制模型 prompt 時，請它直接輸出 JSON 清單。Regex 是不得已的 fallback，準確度永遠不如直接 parse。

04

法規別名表

「個資法」=「個人資料保護法」、「公交法」=「公平交易法」。建立一張別名表做 canonicalization，否則相同法條會被當成不同。

失敗案例分析才是重點

單看 macro F1 = 0.78 沒什麼用，重點是「哪些法條常被漏？哪些常被瞎掰？」failure_analysis() 回傳的 top_missed 跟 top_hallucinated 才是真正能幫你改進模型的訊號。如果某條法規一直被漏掉，可能訓練資料裡的相關案例太少；如果某條法規被亂掛，可能模型把它當成「萬用法條」 — 這些都需要回頭調訓練集。

Layer B 實作：Judge LLM

Layer B 用 LLM 評估「推理過程」這個結構化比對搞不定的部分。關鍵原則 — Judge LLM 不能看 ground truth。它只看案件跟模型的回覆，憑案件本身判斷推理是否合理。

Prompt Template

你是法律推理品質評審員。給你一個案件跟一份分析報告，請評估這份分析的品質。

【你會看到】
- 案件描述
- 一份分析（含「違反法規清單」+「推理過程」）

【你不會看到】
- 標準答案。這是故意的，請根據案件本身判斷分析是否合理，
  而不是去猜「正確答案應該是什麼」。

【評估準則】

針對下列每一項，給 PASS / FAIL，並引用具體文字當證據：

1. 事實認定
   PASS：分析提到的事實，每一個都能在案件描述中找到對應
   FAIL：出現案件沒提到的事實，或誤讀事實

2. 法條適用
   PASS：引用的每條法規，都有清楚對應的案件事實
   FAIL：引用了不適用的法條，或法條與事實的連結太薄弱

3. 推理邏輯
   PASS：從事實到「違反 X 法規」的推論完整，
        沒看過案件的人讀完也能跟上
   FAIL：跳躍推論、循環論證、缺少關鍵推理步驟

4. 遺漏爭點
   PASS：案件中明顯該討論的法律議題都有觸及
   FAIL：有明顯應討論但完全沒提的爭點

【輸出格式】

請輸出純 JSON，不要包 markdown code block：

{
  "criteria": [
    {
      "name": "事實認定",
      "verdict": "PASS",
      "evidence": "案件描述提到『A 公司未經 B 同意收集個資』，
                   分析引用此事實",
      "reasoning": "事實有對應，無編造"
    },
    ...其他三項
  ],
  "overall_pass": false,
  "confidence": "high",
  "notes": "整體觀察"
}

【硬規則】
- 不可猜測「正確答案應該是什麼」
- 不可因為「分析寫得很有自信」就判 PASS
- 每一項 criteria 都必須引用具體文字
- 無法判斷時，verdict 給 FAIL，confidence 給 low

---

【案件】
{case_text}

【分析】
{model_output}

五個關鍵設計決定

01

用 PASS / FAIL，不用評分尺度

1–5 分的 judge 會大量集中在 3–4 分（中庸偏好），實際區辨力很低。Binary 強迫做出判斷，雜訊小很多，跟 Claude Code grader 一致。

02

強制 cite evidence

沒 evidence 的 PASS 是垃圾資料 — judge 可能只是憑感覺。要求引用具體文字，能擋掉一大半的氛圍判斷。

03

明寫「不要猜正確答案」

LLM 訓練資料裡有很多「評估 X 是否正確」的範例，會誘導它去猜答案。明文禁止能顯著降低這種傾向。

04

四項剛剛好

太多 criteria 會讓 judge 分散注意力。三到五項是甜蜜點。這四項刻意涵蓋：事實層 → 法條層 → 推理層 → 完備性，從窄到寬。

05

純 JSON 輸出

明寫「不要包 markdown code block」否則某些模型會自動加 fence，後續 parse 會壞掉。temperature=0 也能提高穩定度。

Python 呼叫範例

import anthropic, json

client = anthropic.Anthropic()

def judge_case(case_text, model_output):
    prompt = JUDGE_PROMPT_TEMPLATE.format(
        case_text=case_text,
        model_output=model_output
    )
    resp = client.messages.create(
        model="claude-opus-4-7",   # judge 用強模型
        max_tokens=2000,
        messages=[{"role": "user", "content": prompt}],
        temperature=0,             # 評分要穩定
    )
    return json.loads(resp.content[0].text)

實作注意事項

方法對了還不夠，幾個容易被忽略但會影響結果可信度的細節：

注意 · Hold-out test set

Fine-tuning 用過的案件絕對不能拿來測，這會讓你測的是「背題能力」而非「推理能力」。從 100 個案件中至少留出 20–30 個作為 hold-out test set，這批資料模型完全沒看過。

注意 · Judge 模型選擇

Judge LLM 必須跟 fine-tuned model 的 base 不同。例如 fine-tune 的是 Llama，judge 就用 Claude 或 GPT。否則會有 self-preference bias — 模型傾向偏好跟自己風格相似的輸出。

注意 · Variance 分析

同一個案件讓 judge 跑三次，取多數決。如果三次結果分歧，這個案件單獨拉出來人工複核，不要直接採信任何一次。這跟 Claude Code skill-creator 跑 3 次取樣本是同樣的設計。

注意 · 人類校準

挑 10–20 個案件先讓人類專家評估一次當對照，看 judge 的判斷跟人類有多接近。如果 agreement < 70%，rubric 要再調 — 可能是評估準則寫得不夠清楚，或是 LLM 對該領域理解不足。

結論

用 LLM 驗證 LLM 是個強大的工具，但用錯了會比沒用更糟 — 它會給你假的安全感。本文的核心主張可以濃縮成三句話：

  1. 分工要清楚。結構化輸出用程式比對，自然語言推理用 LLM 評審。不要把所有事情丟給同一個工具。
  2. Judge 必須 blind。標準答案只給 Layer A 的程式比對；Judge LLM 在不知道答案的狀態下獨立判斷，否則它只是在做相似度檢查。
  3. 失敗案例分析比平均分更有用。Macro F1 = 0.78 只是個數字；「哪些法條常被漏掉」才能告訴你下一步要怎麼改進。

整套架構不複雜，可以在一個下午搭起來。但它能讓你對 fine-tuned model 的能力有真實的、可信的、可重現的了解，這是 fine-tune 流程裡最容易被跳過、卻最重要的一環。
